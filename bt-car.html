Line-Follow / Obstacle-Avoid / Bluetooth Car

Overview

A basic acrylic 4-wheel chassis combining three driving behaviors: line-following, obstacle avoidance, and Bluetooth remote control. A switch picks between line-follow and Bluetooth modes, while ultrasonic obstacle avoidance runs constantly as a safety override on top of whichever mode is active, with no crashes in testing.

Line-following with PID

A 5-sensor IR array (L2, L1, C, R1, R2) gives a proportional line position rather than a simple on/off read. Each sensor returns 0 or 1 depending on whether it sees the dark line, and I weight the five positions to get a single error number instead of just "on the line" or "off it":

weightedSum = (L2×-2) + (L1×-1) + (C×0) + (R1×1) + (R2×2)

error = weightedSum / (L2+L1+C+R1+R2)

If only the center sensor is lit, error = 0 (dead on line). If the line drifts under R1, error comes out positive, telling the car to steer right to re-center. That error is the input to the PID loop:

correction = Kp×error + Ki×Σerror + Kd×(error − lastError)

P (Kp×error) steers proportionally to how far off-center the line is — bigger error, harder correction. I (Ki×running sum of error) catches a persistent drift, like one motor running slightly slower than the other, that P alone settles into but never fully cancels. D (Kd×change in error since the last reading) resists how fast the error is growing, which is what stops the car from overcorrecting and snaking across the line. Each loop, lastError is updated to the current error so the next pass has something to compare against.

The correction term then splits into a speed differential between the two sides:

leftSpeed = baseSpeed − correction

rightSpeed = baseSpeed + correction

Both speeds get clamped to the 0–255 PWM range before being written out, so a large correction slows/reverses one side rather than demanding an out-of-range value.

Bluetooth control protocol

The HC-06 is a slave-only Bluetooth module that implements SPP (Serial Port Profile) — it makes the wireless link look like an ordinary wired serial cable to both sides. On the phone, a Bluetooth RC-car app pairs with the module and opens a serial connection; on the Arduino side, that connection shows up as plain bytes on the hardware UART (D0/D1), read with the normal Serial library like it was a USB cable. Neither side has to think about the Bluetooth radio layer at all.

Out of the box the HC-06 talks at 9600 baud and is configured through AT commands sent over that same serial line while nothing is paired yet — e.g. AT+NAMEBTCAR to set the discoverable name or AT+PIN1234 to set the pairing PIN. Once paired, the module drops out of AT mode and starts passing bytes straight through.

The control scheme itself is just single ASCII characters, one per command, matching what most Android Bluetooth-car apps send by default:

Byte receivedAction
'F'Forward — both motors forward
'B'Backward — both motors reverse
'L'Left — right motor forward, left motor stopped/reversed
'R'Right — left motor forward, right motor stopped/reversed
'S'Stop — both motors off

The main loop calls Serial.available() every pass and, if a byte is waiting, reads it with Serial.read() and switches on it to set motor pin states directly — there's no packet framing or checksum, since a single dropped byte just means the car keeps doing whatever it was already doing until the next character arrives.

One wiring detail the schematic below only labels in passing: the Arduino's TX pin idles/drives at 5V logic, but the HC-06's RX input is rated for 3.3V. Its own TX output is safe to feed straight into the Arduino's RX pin (3.3V still reads as a valid logic-high to a 5V input), but the reverse direction needs a voltage divider so the HC-06 doesn't see 5V on its RX line:

Vout = Vin × R2 / (R1 + R2)

with R1 = 1kΩ, R2 = 2kΩ: Vout = 5V × 2/3 ≈ 3.3V

Obstacle avoidance

Three HC-SR04 ultrasonic sensors (front, left, right) run underneath whichever driving mode is active, checked at the top of every loop iteration regardless of whether the car is currently in line-follow or Bluetooth mode. Each sensor is pulsed and timed the same way: drive its Trig pin high for 10µs to fire a burst of ultrasound, then measure how long the Echo pin stays high while the sensor waits for that burst to bounce back.

That round-trip time converts to a distance using the speed of sound, about 343 m/s, which works out to 0.0343 cm per microsecond. The pulse travels to the obstacle and back, so the raw time is halved:

distance (cm) = (duration × 0.0343) / 2

example: duration = 1200µs → distance = (1200 × 0.0343) / 2 ≈ 20.6 cm

Each of the three readings is compared against a threshold distance (roughly 15cm in testing — close enough to react, far enough to still have room to maneuver). If any sensor reads under the threshold, that reading overrides the current mode's motor output for that loop pass: front-only triggers a stop-and-reverse, a side sensor triggering steers away from that side. Because this check runs every single loop before anything else gets written to the motors, it behaves less like a separate "obstacle mode" and more like a safety clamp sitting on top of whatever line-follow or Bluetooth control just decided — which is why the car had no collisions across testing even while switching between the other two modes.

Motor driver: L298N H-bridge

Both motors are driven through an L298N, a dual H-bridge module. An H-bridge is four switches arranged so current can be pushed through a motor in either direction: closing one diagonal pair sends current one way (motor spins forward), closing the other diagonal pair reverses it, and the L298N exposes that as two logic pins per motor:

IN1IN2Result
HIGHLOWForward
LOWHIGHReverse
LOWLOWCoast (free-spin)
HIGHHIGHBrake (both terminals shorted)

Speed is separate from direction: each motor also has an ENA/ENB pin driven with PWM, so direction comes from IN1/IN2 while speed comes from how long that pin stays high within each cycle (its duty cycle). On an 8-bit PWM pin (0–255):

duty cycle (%) = (pwmValue / 255) × 100

This is the one part all three driving modes share: line-follow's PID correction, the Bluetooth character commands, and the obstacle-avoidance override all boil down to the same two calls per motor — set IN1/IN2 for direction, set ENA/ENB for speed. They're just three different sources deciding what those values should be on any given loop.
